# Shared contracts

Every entity shared between features, the API and (later) the Expo app is defined **once** in [`src/lib/contracts/index.ts`](../src/lib/contracts/index.ts). Each definition is a Zod schema plus its inferred TypeScript type with the same name:

```ts
import { PlannedWorkout } from "@/lib/contracts";

const workout: PlannedWorkout = PlannedWorkout.parse(body); // validates at runtime, typed at compile time
```

**Rules**

- Do not redefine these entities in a feature folder. Feature-private types such as form state or view models are fine; they must not shadow a contract name.
- The lead owns the contracts file. To change it, open a PR labelled `contracts`, explain the change, and have every feature owner approve it. Additive changes, such as a new optional field or a new enum value, are preferred over renames.
- Postgres enums mirror contract enums. Change both in the same PR: a migration plus the contract.

## Identifiers

| Thing           | Format                                                                |
| --------------- | --------------------------------------------------------------------- |
| Every id        | UUID string (`z.uuid()`), generated by Postgres (`gen_random_uuid()`) |
| User id         | Equals Supabase `auth.users.id` and `profiles.id`                     |
| Storage paths   | `{userId}/{uuid}.{ext}` inside a private bucket (e.g. `timetables`)   |
| Programme slugs | lowercase kebab-case, e.g. `couch-to-5k`                              |

## Dates and times

| Kind                                        | Contract type | Example                           | Stored as           |
| ------------------------------------------- | ------------- | --------------------------------- | ------------------- |
| An instant (session start, log time, event) | `IsoDateTime` | `2026-10-20T01:00:00Z`            | `timestamptz` (UTC) |
| A calendar date (report period, week start) | `IsoDate`     | `2026-10-19`                      | `date`              |
| A wall-clock time in a recurring week       | `LocalTime`   | `06:30` (24-hour)                 | `time`              |
| Day of week                                 | `Weekday`     | `1` = Monday … `7` = Sunday (ISO) | `smallint`          |
| Timezone                                    | IANA name     | `Asia/Kolkata` (default)          | `text`              |

- APIs send and receive instants as ISO 8601 strings with an offset (normally `Z`). Convert to the runner's timezone for display only, using `Intl.DateTimeFormat` or `@date-fns/tz`.
- Availability blocks are **recurring** (weekday + local times), not dated. The scheduler turns them into dated `PlannedWorkout`s for a given `weekStart`.
- Durations are integers with the unit in the name: `durationMinutes`, `durationSeconds`, `distanceMeters`.

## Entities

| Area         | Contract                                                                    | Notes                                                                                              |
| ------------ | --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Identity     | `Role`, `UserProfile`, `FitnessLevel`, `PrimaryNeed`                        | Roles: `runner`, `coach`, `mentor`, `programme_manager`, `admin`. Every user is at least `runner`. |
| Preferences  | `UserPreferences`, `FitnessGoal`, `TimeOfDay`                               | Drive the scheduler.                                                                               |
| Scheduling   | `AvailabilityBlock`, `TimetableUpload`, `ExtractedTimetable`                | Any extractor, AI or text parser, must return `ExtractedTimetable`.                                |
| Scheduling   | `PlannedWorkout`, `SchedulerInput`, `SchedulerResult`                       | The scheduler is a pure function `SchedulerInput → SchedulerResult`, with no I/O and no LLM.       |
| Training     | `CompletedWorkout`, `TrainingProgramme`, `ProgrammeSession`, `WorkoutBlock` | `perceivedEffort` is RPE 1–10.                                                                     |
| Community    | `Location`, `CommunityEvent`, `RunnerFeedback`, `Announcement`              | `Location.verified = false` must be shown as "Unverified" in the UI.                               |
| Gamification | `XpTransaction`, `AchievementSummary`, `EarnedBadge`                        | XP is an append-only ledger written only on the server. Totals are derived, never edited.          |
| Reports      | `ReportPeriod`, `ActivityReport`                                            | `week`, `month`, `year`.                                                                           |

## API conventions (`/api/v1/*`)

**Versioning.** All data endpoints live under `/api/v1`. A breaking change goes to `/api/v2`, because old mobile builds keep calling old endpoints.

**Authentication.** Endpoints accept either the web cookie session or `Authorization: Bearer <supabase access token>`. Use `getRequestUser(request)` from `src/lib/auth/request-user.ts`, which verifies the JWT with `getClaims()` and returns a Supabase client acting as the caller, so RLS still applies.

**Success envelope**

```json
{ "data": { "...": "..." } }
{ "data": [ ... ], "meta": { "nextCursor": "opaque-string-or-null" } }
```

**Error envelope**

```json
{ "error": { "code": "validation_failed", "message": "Some fields are missing or invalid.", "details": [ ... ] } }
```

Use the helpers in `src/lib/api/response.ts`: `ok(data)`, `fail(code, message, details?)` and `parseJson(request, Schema)`.

| `code`                   | HTTP | When                                                        |
| ------------------------ | ---- | ----------------------------------------------------------- |
| `bad_request`            | 400  | Malformed request (e.g. invalid JSON)                       |
| `unauthenticated`        | 401  | No valid session or token                                   |
| `forbidden`              | 403  | Signed in but not allowed                                   |
| `not_found`              | 404  | Resource does not exist or is not visible to the caller     |
| `conflict`               | 409  | Duplicate or state conflict                                 |
| `payload_too_large`      | 413  | Upload over the limit (10 MB)                               |
| `unsupported_media_type` | 415  | File type not allowed                                       |
| `validation_failed`      | 422  | Body failed the contract schema; `details` holds Zod issues |
| `rate_limited`           | 429  | Per-user limit hit (e.g. `AI_DAILY_CALL_LIMIT`)             |
| `not_implemented`        | 501  | Endpoint reserved but not built yet                         |
| `ai_unavailable`         | 503  | AI is off or failing; the client should offer the fallback  |
| `internal_error`         | 500  | Anything unexpected                                         |

- `message` is plain English that is safe to show to a runner. Never put stack traces, SQL or secrets in it.
- Log the underlying error on the server; return the generic message to the client.
